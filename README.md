# API Трекера полезных привычек (Django REST Framework + Celery)

Дипломный/курсовой проект бэкенд-системы для отслеживания полезных привычек с автоматическим контролем бизнес-логики и фоновыми уведомлениями.

---

## 🛠 Технологический стек
* **Язык разработки:** Python 3.14+
* **Фреймворк:** Django 4.2+ / Django REST Framework (DRF)
* **Аутентификация:** JWT (JSON Web Token) через `djangorestframework-simplejwt`
* **Фоновые задачи:** Celery
* **Брокер сообщений / Кэш:** Redis (работает в качестве системной службы Windows/Linux)
* **Планировщик:** Django Celery Beat (управление расписанием из базы данных)
* **Документация:** OpenAPI 3.0 / Swagger UI / ReDoc через `drf-spectacular`

---

## 🧭 Основные эндпоинты проекта

При запуске сервера на главной странице (`http://127.0.0`) доступен графический веб-интерфейс с быстрыми переходами:
* `http://127.0.0api/docs/swagger/` — Интерактивная документация Swagger UI с возможностью тестирования API.
* `http://127.0.0api/docs/redoc/` — Строгая техническая спецификация ReDoc.
* `http://127.0.0admin/` — Панель администратора Django.

### Набор эндпоинтов (Routing):
1. **Пользователи (`/api/users/`):**
   * `POST /register/` — Регистрация нового пользователя (авторизация по `email`).
   * `POST /login/` — Получение пары JWT-токенов (`access`, `refresh`).
   * `POST /token/refresh/` — Обновление истекшего `access`-токена.
2. **Привычки (`/api/habits/`):**
   * `GET /` — Просмотр списка личных привычек текущего пользователя (с пагинацией по 5 элементов).
   * `POST /` — Создание новой привычки (автоматическая привязка к `request.user`).
   * `GET /{id}/`, `PUT /{id}/`, `PATCH /{id}/`, `DELETE /{id}/` — CRUD-операции над конкретной привычкой (доступ имеет только владелец объекта).
   * `GET /public/` — Список всех публичных привычек системы (доступен всем авторизованным пользователям только для чтения).

## 🧠 Реализованная бизнес-логика (Валидаторы)
В проекте реализованы жесткие кастомные валидаторы DRF на уровне `HabitSerializer` для соблюдения критериев ТЗ:
1. **Исключение одновременного выбора:** Нельзя одновременно заполнить поле вознаграждения (`reward`) и связанной привычки (`associated_habit`).
2. **Ограничение по времени:** Время выполнения привычки (`time_to_complete` / длительность) должно быть не больше 120 секунд.
3. **Фильтрация связанных привычек:** В связанные привычки могут попадать только те записи, у которых флаг приятной привычки равен `is_pleasant=True`.
4. **Ограничения приятной привычки:** У приятной привычки (`is_pleasant=True`) не может быть вознаграждения или связанной привычки.
5. **Ограничение периодичности:** Привычку нельзя выполнять реже, чем 1 раз в 7 дней (значение поля `periodicity` не может превышать 7).

## 📢 Особый режим симуляции Telegram (Graceful Degradation)

В связи с инфраструктурными сетевыми ограничениями доступа к официальным серверам `api.telegram.org` на уровне провайдеров/DNS, архитектура уведомлений переведена в режим **Mock-тестирования (Логирования)**.

### Как это работает:
Периодическая задача Celery Beat запускается каждую минуту, сканирует базу данных и находит привычки, время выполнения которых совпадает с текущим моментом. Вместо отправки запроса в сеть, бот формирует полноценное тело сообщения и аккуратно записывает его в файл автономной истории **`telegram_history.log`** в корне проекта. Это гарантирует 100% стабильность демонстрации логики планировщика без сетевых сбоев.

## 🚀 Инструкция по запуску всей архитектуры

Для полноценной демонстрации работы фоновых уведомлений необходимо открыть 3 параллельные вкладки терминала в PyCharm и запустить компоненты:

### Вкладка 1: Основной веб-сервер Django
```bash
python manage.py runserver
```

### Вкладка 2: Фоновую службу исполнителя Celery Worker
```bash
celery -A config worker -l info -P eventlet
```

### Вкладка 3: Периодический планировщик Celery Beat
```bash
celery -A config beat -l info
```

*Перед запуском убедитесь, что локальная служба **Redis** активна и запущена в системе на порту `6379`.*


## 🧪 Тестирование и покрытие кода (Coverage)

В проекте реализовано модульное тестирование основных компонентов (Views, Permissions, Validators, Serializers) с использованием встроенного инструмента `django.test` и библиотеки `coverage`.

**Итоговый результат покрытия кода составляет 82%**, что полностью удовлетворяет и превосходит требования технического задания (80%+).

### Инструкция по генерации отчета:
1. Запуск тестов и сбор статистики:
   ```bash
   coverage run --source='.' manage.py test
   ```
2. Вывод текстового отчета в консоль:
   ```bash
   coverage report
   ```
3. Генерация интерактивного HTML-отчета:
   ```bash
   coverage html
   ```
